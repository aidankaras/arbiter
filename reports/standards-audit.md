# Standards audit — 2026-09-19

**Verdict.** The built code — ingestion, event extraction, the Parquet store,
market-data fetching, label resolution, the baseline arm, its evaluation
harness, and the append-only ledger schema — held up against every
point-in-time, batching, silent-failure, and statistical-validity check run
against it; no demonstrable defect surfaced in `src/arbiter/arms/features.py`,
`src/arbiter/evaluation/resolution.py`, `src/arbiter/arms/evaluate.py`,
`src/arbiter/evaluation/metrics.py`, or the ingestion/market modules, and the
unit-test suite's negative controls (an evaluation given a genuinely
uninformative signal, an entry-timing test for pre-market filings, a
per-item-isolation test for batched price requests) are real properties, not
restatements of the code they guard. The defects that are demonstrable cluster
in two places instead: a migrations file whose autogenerate target is silently
empty, which is a latent threat to the append-only ledger the whole project
depends on, and documentation — `docs/`, `README.md`, `reports/README.md` —
that in several places describes unbuilt subsystems as already implemented,
including the one document whose entire subject is proving the project's
central point-in-time claim.

## Findings

### 1. `migrations/env.py` never imports the ORM models, so autogenerate's target schema is empty

`migrations/env.py:16` imports `Base` from `arbiter.db.base`, and line 24 sets
`target_metadata = Base.metadata`. Neither `arbiter/db/__init__.py` (a bare
docstring) nor `env.py` itself imports `arbiter.db.models`, and no version
script does either — `0001` and `0002` are hand-written (`op.create_table`,
`op.add_column`), not autogenerated. `Prediction` and `LlmCall`
(`src/arbiter/db/models.py`) only register themselves on `Base.metadata` when
that module is imported; nothing in the process that runs `env.py` does so.

Concrete failure: running `uv run alembic revision --autogenerate -m "..."` —
the documented way to add a third migration — against a database already
migrated to head compares the live schema (`predictions`, `llm_calls`, their
indexes, constraints, and the append-only trigger) against a `target_metadata`
holding zero tables. Alembic would emit `op.drop_table("predictions")` and
`op.drop_table("llm_calls")` as the autogenerated diff. `tests/integration/
test_migrations.py` only calls `command.upgrade(config, "head")`, which runs
the existing scripts' `upgrade()` bodies directly and never touches
`target_metadata`, so this has never been exercised by the suite.

This is exactly the failure mode CLAUDE.md's non-negotiables #1 and #4 exist to
prevent — a prediction row deleted or a packet's provenance lost — except the
tool that would do it is the migration tooling itself, and it would do it
silently, since Alembic considers a normal, up-to-date-looking diff.

**Fix:** import `arbiter.db.models` (e.g. `import arbiter.db.models  # noqa: F401`)
before line 24 so every mapped table is registered before `Base.metadata` is
read.

### 2. `docs/lessons/01-point-in-time-correctness.md` describes the packet and retrieval layer as built and tested, contradicting its own status line and the rest of the tree

Lines 4–6 state the file's status plainly: "the ingestion half is implemented,
the packet and retrieval half is not... nothing here should be read as
describing code that exists unless it says so." The "How it is implemented"
section (lines 81–93) then states, unqualified:

- Line 83–85: "The `as_of` timestamp is a required field on the packet, not an
  optional parameter with a default."
- Line 87–89: "Every retrieval path carries a test that inserts a comparable
  resolving after the event timestamp and asserts it is excluded."
- Line 91–93: "Packets are content-hashed and every prediction stores the
  hash..."

None of this exists: `src/arbiter/` has no `packets` or `retrieval` package
(`Glob src/arbiter/**/packet*` and `**/retrieval*` both return nothing), no
`hashlib` or content-hashing call anywhere in `src/`, and `docs/methodology.md:83-84`
says the opposite in the same repository: "Every retrieval path will carry a
test... no retrieval code exists yet." `docs/architecture.md`'s own module
table lists `packets` and `retrieval` under "Modules the design calls for, not
yet written." This is the one document whose entire subject is the project's
central validity claim, and its "implemented" section describes the opposite
of what is in the tree.

**Fix:** apply the file's own stated convention — mark the "How it is
implemented" section as the design, not as delivered, until `packets/` and
`retrieval/` exist.

### 3. `docs/architecture.md` states a limitation that the schema already removed, and a schedule that does not exist

- Lines 139–143: "Attribution to a packet and a prediction is the goal and is
  not yet possible: the ledger table carries no packet hash or prediction
  reference, so cost per decision cannot be computed until those columns and
  the predictions that populate them exist." This is contradicted by
  `src/arbiter/db/models.py:85-88`, where `LlmCall.packet_hash` and
  `LlmCall.prediction_id` already exist, added by
  `migrations/versions/0002_attribute_cost_and_deduplicate_predictions.py`
  (titled, not coincidentally, "Attribute cost... to its decision"). The
  columns this paragraph says do not exist have existed since that migration
  merged.
- Lines 122–135, "Scheduling and deployment": "Scheduled work runs on GitHub
  Actions," followed by a table of daily/weekly/monthly ingestion, evaluation,
  and dashboard-publication jobs. `.github/workflows/` contains four files:
  `ci.yml` (push/PR), `claude.yml` (issue comments), `claude-code-review.yml`
  (PRs), and `standards-audit.yml` (`cron: "0 9 1,15 * *"` — this audit,
  bimonthly). None runs `arbiter ingest`, `arbiter resolve`, or `arbiter
  report`, and no dashboard-building step exists anywhere in the repository.

**Fix:** mark both as planned, consistent with the same document's "Storage"
and "Modules" sections, which already separate "today" from "planned."

### 4. `README.md`'s roadmap contradicts its own status banner and the code

Lines 16–23 state plainly: "Working today: ... the baseline forecasting arm,
out-of-sample evaluation by information coefficient and calibration..." Line
247 nonetheless reads `- [ ] Baseline arm and evaluation harness` — unchecked,
in the same file that just said it was working. `src/arbiter/arms/baseline.py`,
`src/arbiter/arms/evaluate.py`, `src/arbiter/evaluation/report.py`, the
`arbiter report` CLI command (`src/arbiter/cli.py:135-169`), and
`tests/unit/test_baseline_evaluation.py`/`test_baseline_model.py`/`test_report.py`
all confirm it is built. The roadmap checkbox was not updated when the arm
landed.

### 5. `reports/README.md` describes a file that is not in this branch

Lines 7–12, under the heading "## What is here now": "`baseline-insider.md` —
the conventional arm measured out of sample, written by `arbiter report`."
`reports/` on `main` (`267dcb9`) contains only `README.md`; `baseline-insider.md`
exists solely on the unmerged branch `origin/first-measurement`
(`git cat-file -e HEAD:reports/baseline-insider.md` fails; `git cat-file -e
a587237:reports/baseline-insider.md`, a commit on that branch, succeeds). A
reader of `main` is told a result is here now that isn't.

### 6. `README.md`'s Stack section drops the tense discipline the same document declares

Lines 19–28 explicitly separate "Working today" from "Designed but not built"
and state the rule: "Sections describing those use the future tense; anything
in the present tense refers to code in this repository." The "Stack" section
(lines 219–224) does not follow it: "LangGraph for orchestration. FastAPI for
the API and dashboard. ... Docker Compose for local and deployed environments.
GitHub Actions for scheduled ingestion, evaluation, and reporting" sit as bare
present-tense clauses next to "Ingested events are stored as date-partitioned
Parquet," which is built. `langgraph`, `fastapi`, `uvicorn`, and `jinja2` are
imported nowhere in `src/` (all four are declared only as unused optional
extras in `pyproject.toml`); there is no `docker-compose.yml` anywhere in the
repository (only a single-stage `Dockerfile`); and no scheduled workflow runs
ingestion, evaluation, or reporting (see Finding 3). A reader following the
document's own stated rule would read this paragraph as a list of things that
run today.

### 7. `docs/strategies/insider.md`'s feature table lists a feature the code deliberately excludes, one that doesn't exist, and mischaracterizes a third

- Line 21: "Rule 10b5-1 plan indicator" is listed as a model feature.
  `src/arbiter/arms/features.py:38-41` documents the opposite decision:
  "`is_10b5_1` is absent for the stronger reason that the screen admits no
  scheduled trade at all, leaving the column constant... its fitted weight
  would be noise printed in the report as though it meant something." It is
  used only as a screening criterion (`events/insider.py`'s `is_candidate`),
  never as a feature — `is_10b5_1` is not in `FEATURE_NAMES`.
- Line 20: "Days to the next scheduled earnings event" — no earnings/XBRL code
  exists anywhere in the repository, so this cannot be computed; it is not in
  `FEATURE_NAMES`.
- Line 19: "Cluster flag | Multiple insiders transacting within a rolling
  window" — the implemented feature, `insiders_trading_same_issuer`
  (`features.py:127`, computed by `day_features` at `features.py:131-145`),
  counts distinct insiders filing on the *same calendar day*; there is no
  rolling window (no multi-day lookback) anywhere in the feature code.

### 8. `pgvector` and `structlog` are declared dependencies with no importer

`pyproject.toml`'s core `dependencies` list includes both. Neither is imported
anywhere in the repository (`src/`, `tests/`, `migrations/`, `scripts/`) —
confirmed by an unrestricted grep for `import pgvector`/`from pgvector` and
`import structlog`/`from structlog`. `pgvector` is explained by
`docs/architecture.md`'s own "planned, once comparable retrieval exists"
note, so it is a deliberate pre-declaration rather than a mistake, but it is
still a supply-chain surface and a `pip-audit` finding waiting to happen for
code that does not exist yet. `structlog`'s absence is total: no logging
statement of any kind appears in `src/`, and `Settings.log_level`
(`src/arbiter/config.py:53`) configures nothing that reads it.

## What was checked and found sound

- **Point-in-time integrity**: `entry_sessions`, `window_closes_on`,
  `sessions_after`, `plan_price_windows`, `resolve_label`, and `day_features`
  / `load_day`'s feature-before-labelling ordering (`arms/evaluate.py:94-100`,
  guarded by `tests/unit/test_point_in_time_features.py`) all compute from
  what was knowable at `as_of`, and the apparent same-day-vs-next-day
  entry-timing question is deliberately and correctly always-next-day, because
  the pipeline is a nightly batch (`tests/unit/test_resolution_pipeline.py:49-54`
  documents and pins this).
- **Errors correlated with the data**: session-count arithmetic
  (`sessions_after`) walks the real trading calendar rather than approximating
  by weekday, and `_paired_sessions` in `resolution.py` re-indexes issuer and
  benchmark bars by calendar date rather than by position, specifically to
  avoid a halt-correlated bias.
- **Batching**: `daily_bars_tolerating_gaps`/`_bars_isolating_rejections`
  (market.py) isolate a single rejected symbol by bisection rather than
  failing the whole window; `with_tickers` and `ingest_day` isolate one
  unpriceable issuer or one malformed filing from the rest of a day; each path
  has a systemic-rate guard (`_SYSTEMIC_REJECTION_RATE`,
  `_SYSTEMIC_UNMEASURABLE_RATE`, `_SYSTEMIC_FAILURE_RATE`) that turns "too many
  bad items" into a raised error instead of a quietly thin dataset.
- **Silent failure**: exclusions (`unpriceable/`, `rejected/`) are recorded
  with a reason and a per-day partition rather than dropped; the two `except
  Exception` blocks in `src/` (`db/session.py`, `ingestion/backfill.py`) both
  re-raise or record per item rather than swallowing.
- **Statistical validity**: `information_coefficient` and `summarise_ic` pool
  at issuer-day, not filing, and average across days rather than pooling
  observations within a day; `evaluate_baseline`'s train/test split is
  chronological and tested to reject a random split
  (`test_baseline_evaluation.py`); `test_outcomes_independent_of_the_features_yield_no_measurable_skill`
  is a genuine negative control with an independently-constructed
  ground truth, not an assertion on the code's own output.
- **Tests**: spot-checked `test_market_contract.py`, `test_resolution_pipeline.py`,
  `test_baseline_evaluation.py`, and `test_point_in_time_features.py` for
  self-referential assertions; none found. The suite could not be executed in
  this sandbox (`uv` is not installed and no other invocation of `pytest` is
  permitted here), so "green" is not independently confirmed by this audit;
  the assessment above is from reading, not from a run.
